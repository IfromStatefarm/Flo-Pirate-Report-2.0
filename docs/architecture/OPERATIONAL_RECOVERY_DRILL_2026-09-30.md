## Remaining staging drill

Record the source commit plus a fingerprint of uncommitted source, extension ZIP digest and ID, staging branch and function revision IDs, UTC start/end times, and sanitized provider resource IDs. Store logs without OAuth tokens, refresh tokens, private file contents, personal data, or report URLs. Run on a staging database branch with **two unrelated synthetic customers**, separate Google connector credentials and private Drive roots/workbooks that have never been registered to a production customer. Confirm the staging branch points only to those resources before any write.

1. **Two-customer and identity check.** Sign in as an approved and a denied identity for each customer through the deployed staging API. Verify customer A cannot enumerate, open, reconcile, or submit with B's resource IDs, and vice versa. Check current connector ACLs and ancestry by reading the provider files under each root. Run the restricted-login preflight against the staging runtime credential and record the exact role and grant result without its connection string.
2. **One logical report across retries.** Capture one harmless synthetic target and evidence item per customer; disable any real takedown submission. Record the queue item, stable upload request ID, event ID, report ID, journal row, generated report row, projection row, and provider file count. Retry the same command and restart the installed extension worker between capture, evidence upload, PDF generation/upload, batch finalization, projection, and cleanup. After each restart, verify exactly one accepted logical report and one reward/projection, with retained local evidence until acceptance.
3. **Ambiguous live upload.** In staging, let the Google write commit, then cut the response before the API records success. The journal must remain `uncertain`; an ordinary retry must cause zero extra provider writes. Run `reconcile_google_upload` with the entire original command and ID using the authorized identity. Require exactly one file matching operation key, owner/event metadata, name, MIME, size, SHA-256, and original folder ancestry. Confirm one completed receipt and no second upload. Repeat with missing, duplicate, and tampered provider evidence; each must remain uncertain and require operator investigation. Follow [upload reconciliation](UPLOAD_RECONCILIATION.md) for the command shape.
4. **Provider drift.** Revoke the staging connector's access and move a staging child out of its registered root in separate runs. Verify reads and completed-command replay fail closed, no new report is accepted, and neither customer's connector can use the other's resources. Restore the intended staging ACL/ancestry and verify recovery without issuing a replacement ID for an uncertain write.
5. **Backup, billing, alert, and rollback.** Preserve a staging snapshot or dump, deliberately change a disposable marker, restore into a new branch, and compare representative row hashes and counts before an application cutover rehearsal. Deploy the billing worker only with staging secrets and a disposable signed billing event, invoke the scheduled path, and verify idempotent processing and a failed-job alert reaching its destination. Trigger an operational alert for an unresolved journal/projection or failed worker, acknowledge it, and record time to detection. Deploy a prior **compatible** staging function revision, then roll forward to the candidate and verify health, identity, tenant denial, and journal continuity. Do not run destructive schema rollback or swap the production restore preview.

Attach sanitized request/response status, journal transitions, provider file counts and hashes, database query results, worker restart times, snapshot/restore IDs, billing worker invocation and event status, alert receipt, and rollback revision IDs to this record. Close the gate only when every row has direct staging evidence and the observed outcome matches the criteria above. Until then, continue the general-release hold.
