# Tiered Access System — Implementation Outline

## 1. Goal

Add role-based and platform-based access control to the FloSports Pirate Reporter extension. Users create and log in with extension credentials, while the current Google identity supplies the immutable account email in column D. The access registry is stored in the first worksheet (`gid=0`) of the [FloSports access-control spreadsheet](https://docs.google.com/spreadsheets/d/1kp5n1F0cO57P3mbUsgmssXTRIQ3UPdkO6vOKUjV_XvY/edit?gid=0#gid=0).

The system has four access levels:

1. `Waiting_Approval`
2. `Employee`
3. `Manager`
4. `Admin`

These exact values are written to and displayed from column E. The implementation may normalize them to lowercase identifiers internally for comparisons.

Roles are cumulative: a manager receives employee permissions, and an admin receives manager and employee permissions.

## 3. Google Sheet Contract

Use row 1 as the header row and one row per user beginning on row 2.

| Column | Header | Format |
| --- | --- | --- |
| A | `First Name` | Required first name exactly as it should appear on report forms |
| B | `Last Name` | Required last name exactly as it should appear on report forms |
| C | `Middle Name` | Middle name or initial used only when the first/last combination is shared by more than one user |
| D | `User Email` | Lowercase, trimmed email; immutable identity key in the admin UI |
| E | `Access Level` | One of `Waiting_Approval`, `Employee`, `Manager`, or `Admin` |
| F | `Platforms` | Comma-separated canonical platform IDs, or `all` |
| G | `Password Hash` | Salted PBKDF2-SHA-256 credential generated by the extension; never plaintext; `Password` is also accepted |
| H | `Google Drive Root Folder ID` | Optional administrator-managed Drive folder endpoint |
| I | `Google Drive Root Folder Name` | Friendly name displayed instead of the column H ID |
| J | `Foundation Log Sheet ID` | Optional administrator-managed foundation sheet endpoint |
| K | `Foundation Log Sheet Name` | Friendly name displayed instead of the column J ID |
| L | `Event Config Sheet ID` | Optional administrator-managed event configuration endpoint |
| M | `Event Config Sheet Name` | Friendly name displayed instead of the column L ID |

Example:

| First Name | Last Name | Middle Name | User Email | Access Level | Platforms | Password Hash | Drive ID | Drive Name | Foundation ID | Foundation Name | Event ID | Event Name |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Jane | Smith |  | jane.smith@example.com | Manager | youtube,tiktok,instagram | `pbkdf2_sha256$...` | `folder-id` | FloSportsA1 | `sheet-id` | Foundation A1 | `config-id` | Events A1 |
| Alex | Jones | Taylor | alex.jones@example.com | Waiting_Approval |  | `pbkdf2_sha256$...` |  |  |  |  |  |  |
| Pat | Admin |  | pat.admin@example.com | Admin | all | `pbkdf2_sha256$...` |  |  |  |  |  |  |

Rules:

- Compare emails case-insensitively after trimming whitespace.
- Use the canonical IDs already defined by the application's platform catalog, such as `youtube`, `tiktok`, `instagram`, `facebook`, `kick`, `twitter`, `twitch`, `rumble`, `discord`, and `other`.
- Store selected platforms in a stable, comma-separated order with no duplicates.
- Treat blank, unknown, or malformed access levels as `Waiting_Approval`.
- Treat a blank platform cell as no platform access. `all` grants every platform currently registered by the application.
- Resolve worksheet ID `gid=0` to its worksheet title through spreadsheet metadata before using the Sheets values API; do not assume the tab name.
- Reject or flag duplicate email rows. Email must behave as the unique user identifier.
- Compare first/last and middle names case-insensitively when resolving login candidates.
- When the column A/B combination is duplicated, require a middle name or initial in column C. If that complete name is still duplicated, require the user to select their column D email before password verification.
- Never display, return, log, or allow administrators to edit the password hash through the extension UI.
- For each H/I, J/K, and L/M pair, the ID is the operational value and the name is display-only. A blank ID keeps that setting user-editable.

## 4. Bootstrap Requirement

Before the feature is enabled, manually populate the first administrator's first name, last name, email, `Admin` role, and platforms in columns A, B, D, E, and F, then leave column G blank. The matching Google account can use **Create User** in Settings to create its password without losing the seeded admin role. Without a seeded admin, every newly created user receives `Waiting_Approval` and nobody can approve accounts.

Also confirm that the extension's Google OAuth client can read and update this spreadsheet. With the current direct Sheets integration, each user needs sufficient spreadsheet access to create their first row. For a real security boundary, use a small owner-run API or Google Apps Script web app instead of sharing edit access to the registry with all users; otherwise a user could bypass the extension and edit the sheet directly.

## 5. Central Access Model

Create one access-control module as the source of truth rather than scattering role checks through the UI.

Suggested profile shape:

```js
{
  rowNumber: 7,
  name: "Jane Smith",
  middleName: "Taylor",
  email: "jane.smith@example.com",
  role: "manager",
  platforms: ["youtube", "tiktok"],
  status: "ready"
}
```

Suggested permission keys:

```text
sidepanel.report
sidepanel.scoreboard
sidepanel.automate
sidepanel.intel
sidepanel.repair
settings.coreConnectivity
settings.feedbackComms
settings.intelligenceTools
settings.adminAccess
```

The module should provide:

- Role normalization and validation.
- Platform normalization and validation.
- `hasPermission(profile, permission)`.
- `hasPlatformAccess(profile, platform)`.
- `requirePermission(...)` and `requirePlatformAccess(...)` guards for privileged background actions.
- Profile fetch, credential-backed account creation, login/logout, update, cache, refresh, and invalidation functions.

Keep the Google Sheet ID in one constant or managed configuration value:

```text
1kp5n1F0cO57P3mbUsgmssXTRIQ3UPdkO6vOKUjV_XvY
```

## 6. Login and Approval Flow

1. When no extension session exists, Settings shows only Log In and Create User controls; protected settings remain hidden.
2. Account creation obtains the current Google Workspace email, requires separate first- and last-name fields, validates a 12-128 character password, and stores a salted PBKDF2 hash in column G.
3. If the first/last combination in columns A and B is already used, account creation requests a middle name or initial and saves it in column C.
4. A brand-new row receives `Waiting_Approval` in column E and a blank Platforms cell in column F. A matching legacy/seeded row with blank column G can be claimed without changing its existing role or platforms.
5. Login first matches columns A and B case-insensitively. Duplicate matches require column C; duplicate complete names require a column D email selection. Password verification and the active Google identity check then authenticate the selected row.
6. Store the authenticated login in `chrome.storage.session`, so it survives service-worker restarts but ends with the browser session. Do not store the supplied password.
7. Re-read the sheet and refresh role/platform access on every successful login, every Settings-page open, the Settings retry/refresh action, and the side-panel **Open Settings** action.
8. Provide Log Out in Settings and clear the authenticated session and cached access profile when used.
8. Fail closed when identity, credentials, or sheet access cannot be verified.

The waiting-approval Settings view shows only the extension account card, the signed-in user, pending status, and Log Out. It must not expose side-panel tabs or protected settings.

To avoid duplicate account-creation rows, re-check the email immediately before appending. An owner-run API should make this an atomic upsert; a direct Sheets implementation should at minimum detect and report duplicates.

## 7. Side-Panel Changes

Apply access before activating or displaying any tab.

- `Employee`: show **Report** and **Scoreboard**.
- `Manager`: show **Report**, **Scoreboard**, **Automate**, and **Intel**.
- `Admin`: show every side-panel tab, including **Repair**.
- `Waiting_Approval`: hide the entire tab bar and show only the pending-access state.

Implementation details:

- Add permission metadata to each tab button and panel, or map the existing `data-tab-target` values to permission keys.
- If a saved/active tab is unauthorized, select the first allowed tab instead.
- Do not initialize listeners, sheet scans, intelligence generation, or repair tools for inaccessible tabs.
- Re-evaluate the current view when a refreshed profile changes.
- Never rely only on `display: none`; privileged messages and workflows must also be denied in the background layer.

## 8. Platform Access Behavior

Role permission and platform permission are both required for platform-scoped work.

- Report: reject queued or active-page URLs for platforms outside the user's list.
- Automate: show only allowed platforms in scan controls and reject disallowed scan/report requests in the background.
- Intel: restrict platform-specific input and generated results to allowed platforms. If the current briefing cannot be filtered safely, block Intel until server-side/data-layer filtering is added rather than returning broader data.
- Repair: show only allowed platform choices to admins and validate the selected platform again when recording or saving repair data.
- Content scripts and overlays: do not expose reporting/repair actions on a disallowed platform.
- Scoreboard: keep team-wide by default because the requested behavior grants the tab by role and does not define platform filtering for it. Change this only if platform-limited scoreboard data is desired.

Use the shared platform registry/catalog for URL-to-platform detection so UI and background checks cannot disagree.

## 9. Settings-Page Changes

Wrap the existing settings sections in permission-aware containers and gate the page immediately after identity is resolved.

- Employees: **Core Connectivity** and **Feedback Comms**.
- Managers: employee sections plus **Intelligence & Config Tools**, including **Configure Briefing Stats** and **Edit Briefing Content**. **Edit Selector Paths** stays hidden and inaccessible.
- Admins: manager sections plus the new **Admin Access Management** section.

Only load, bind, or save controls the user can access. Hidden fields must not be written with empty or stale values when the general Save button is clicked. Direct navigation to the options page must perform the same authorization checks as navigation from the side panel.

## 10. Admin Access Management

Add an admin-only section to Settings with an **Open User Access Manager** button. The button opens a modal/popup containing:

- Search input that filters by first/last name, middle name, or email.
- Search results showing name, email, access level, and platform summary.
- Editable **First and Last Name** and **Middle Name or Initial** fields.
- Read-only **User Email** field so the identity key cannot be accidentally changed.
- **Access Level** select with all four supported roles.
- **Platforms** multi-select populated from the shared platform catalog, including a convenient **All platforms** option.
- Save and Cancel buttons.
- Loading, empty, success, validation-error, and API-error states.

Admin update flow:

1. Confirm the current user is still an admin using fresh sheet data.
2. Locate the target row by normalized email, not by a stale row number alone.
3. Validate the edited name, access level, and platform list.
4. Update name columns A-C, access columns E-F, and optional managed connectivity columns H-M in one request; leave identity column D and password column G unchanged.
5. Re-read the saved row and refresh the result list.
6. Invalidate the target user's cached profile where possible; otherwise their next scheduled/manual refresh picks up the change.

Safeguards:

- Do not allow removal or demotion of the final admin.
- Warn before an admin changes their own role or removes their own platform access.
- Prevent formulas or spreadsheet control characters from being written as user-entered names.
- Disable Save during a request to prevent duplicate updates.
- Prefer a separate audit worksheet for admin changes with actor email, target email, old value, new value, and timestamp.

## 11. Enforcement Boundaries

UI visibility is presentation, not authorization. Enforce access again wherever work is performed:

- Every privileged message handled by the background service.
- Google Sheet scans and updates.
- Intelligence report generation.
- Repair/selector and macro workflows.
- Content-script commands that capture, queue, autofill, or submit platform data.

Each request should derive the caller identity from Chrome/Google identity and load the current access profile. Do not trust a role, email, or platform list sent in the request payload by the page or side panel.

## 12. Error and State Handling

Define distinct states so the interface gives the correct instruction:

- `loading`: identity/access lookup is in progress.
- `ready`: a valid approved profile was loaded.
- `waiting_approval`: the internal state indicating that the user exists but has no approved role.
- `identity_error`: Google identity is unavailable.
- `registry_error`: the sheet/API cannot be reached or parsed.
- `access_denied`: the role or platform does not permit the requested action.

All denied actions should be logged to the extension console without exposing OAuth tokens or the full access registry.

## 13. Suggested File-Level Work

- `utils/auth.js`: retain Google email lookup; add only identity helpers needed by access loading.
- New `utils/access_control.js`: roles, permission matrix, normalization, cache, and guard functions.
- New `services/access_registry.js` or equivalent background service: sheet lookup, credential hashing, account append/claim, login/logout, list/search users, and admin update operations.
- `background/main.js`: expose narrow access-registry message handlers and guard existing privileged actions.
- `sidepanel.html` and `sidepanel/main.js`: access loading, pending/error state, tab filtering, active-tab fallback, and platform filtering.
- `options.html` and `options/main.js`: settings-section filtering and the admin user-management modal.
- `utils/google_api.js`: reuse the existing authenticated request/error-handling patterns; keep access-registry ranges and parsing isolated from report-sheet logic.
- `utils/platform_catalog.js` / shared platform registry: provide the canonical list used by column F and the admin multi-select.

## 14. Delivery Phases

### Phase 1 — Access foundation

- Seed the first admin.
- Add the role/permission model and sheet registry client.
- Add credential-backed `Waiting_Approval` account creation.
- Add loading, pending, and verification-error states.

### Phase 2 — UI gating

- Gate side-panel tabs.
- Gate settings sections.
- Apply platform filtering to visible controls and page overlays.

### Phase 3 — Operation enforcement

- Guard background actions and content-script workflows.
- Filter platform-specific data at its source.
- Add cache refresh/invalidation behavior.

### Phase 4 — Admin management

- Build user search and edit modal.
- Add validation, final-admin protection, and optional audit logging.

### Phase 5 — Verification and rollout

- Test every role and supported platform combination.
- Test account creation, login/logout, approval, promotion, demotion, and platform changes.
- Test direct navigation and manually crafted runtime messages.
- Roll out first to seeded admins, then managers, then employees.

## 15. Acceptance Criteria

- A newly created extension user is registered exactly once with `Waiting_Approval`, no platform access, and a salted password hash.
- Account creation stores the report-form first and last names in columns A and B and requests a column C middle name or initial only when that pair is already shared.
- Login requests a middle name for duplicate column A/B matches and an email selection when the complete first, middle, and last name remains ambiguous.
- Logged-out users can see only the Settings authentication surface and cannot execute protected actions.
- Login, every Settings open, the Settings retry button, and the side-panel **Open Settings** action refresh role and platform access from the sheet.
- A waiting user cannot see or execute protected features.
- An employee sees only Report and Scoreboard in the side panel and only Core Connectivity and Feedback Comms in Settings.
- A manager receives all employee access plus Automate, Intel, and Intelligence & Config Tools, including Configure Briefing Stats and Edit Briefing Content.
- An admin receives all manager access plus Repair and Admin Access Management.
- A user's platform list limits every platform-scoped UI control and operation.
- An admin can search users and update name, role, and platforms without changing the identity email.
- Changes take effect after refresh (or immediately when cache invalidation is available).
- Direct options-page URLs and crafted background messages cannot bypass permissions.
- Invalid rows, API failures, duplicate emails, and unknown roles fail closed with actionable error messages.
- The final administrator cannot be accidentally removed or demoted.
